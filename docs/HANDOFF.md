# Annual committee handoff

Use this as a private handoff record. Do not commit completed account names, resource IDs, roster data or configuration files to the public repository.

## Record for the current edition

| Item | Value to record privately |
|---|---|
| Edition and release | Year, repository commit/tag, configuration export date |
| Operating ownership | Google account or institutional owner, recovery/contact process, authorized editors |
| Data | Seven workbook links, approved asset folder, document templates, backup location |
| Projects | Five Apps Script editor links, deployment IDs and `/exec` URLs |
| Website | Domain/CMS, page paths, maintainer, embed snippets |
| Background jobs | Reminder sender/trigger owner, calendar owner, cadence and stop functions |
| Authorization | Advanced services enabled, account restrictions, guide-key location if used |
| Acceptance | Date tested, fictional test records, issues and sign-off owner |
| Retention | Archive location, participant-data retention decision, current support contact |

## Turn over an edition

1. Export the current private configuration and make an approved backup of edition data. Record the tested repository commit.
2. Decide who remains responsible for old certificate links, author downloads and the historical program. Document that separately from next year's deployment.
3. Stop obsolete reminder/sync triggers only after the outgoing committee confirms their duties have ended. Stopping a trigger does not require deleting data or historical deployments.
4. Give the incoming committee the generic repository, this record and operational lessons. Share private data only when needed and authorized.
5. The next committee creates a fresh template kit and fresh projects under its own operating account. It fills new rosters and dates; it must not reuse the previous calendar or production resource IDs accidentally.
6. Contribute reusable fixes to the toolkit with schema updates and tests. Keep annual participant data out of commits.

An existing trigger belongs to its creator; copying source does not transfer authorization or ownership. Each edition must authorize and create its own triggers. Keep at least two people familiar with recovery and handoff, using institutional account policies rather than shared passwords in documents.
